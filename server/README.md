# 服务端部署说明

PHP 8.2 + MySQL 5.7，单目录、无 Composer 依赖、无框架。

## 一、部署（3 步）

1. 把整个 `server/` 目录上传到网站根目录，保证浏览器能访问到 `https://你的域名/server/install.php`。
2. 打开 `install.php`，按页面提示填数据库信息和管理员账号。
   安装器会自动：检测环境 → 建库（可选）→ 建 25 张表 → 生成 `lib/config.php` → 创建管理员 → 写 `install.lock`。
3. 装完删掉 `install.php`（不删也行，锁文件会拦住重复安装）。

前台不需要单独构建，`index.html` 直接打开就能连上。

## 三、权限要求

| 路径 | 权限 |
|---|---|
| `lib/` | 可写（安装器要生成 `config.php`） |
| `runtime/` | 可写（限流计数），装完可改为 775 |
| 其余 | 只读即可 |

Nginx 建议再加一条，禁止直接访问 `lib/`：

```nginx
location ~ ^/server/lib/ { deny all; }
```

Apache 用户在 `server/lib/` 放一个 `.htaccess` 写 `Require all denied` 即可（已附带）。

## 四、前台如何连接

前端只有一处需要改：`js/net/api.js` 顶部的 `BASE`。

```js
const BASE = 'server/api/index.php';   // 同域相对路径
```

如果服务端在别的域名，写成完整地址，并把 `server/lib/config.php` 里的
`site.cors` 设成你的前端域名。

**未登录也能玩**：前端会自动进入「游客模式」，存档只存在浏览器本地。
登录后自动把本地存档合并上云，并解锁业力遗产、判官陪审、排行榜等联网玩法。

## 六、棋盘中央广告位

游戏中央广场有三类广告位，内容全部来自数据库 `ads` 表，改完后台刷新即生效，
不用碰前端代码：

| slot | 位置 | 面数 | 画面比例 |
|---|---|---|---|
| `tower` | 社会时钟塔 · 塔身四面 | 4 | 2.0 × 2.5 米（画布 512×640） |
| `pillar` | 四柱灯箱 · 每根柱子前后两面 | 8 | 1.16 × 1.72 米（画布 512×768） |
| `ground` | 地面地贴 · 四块 | 4 | 3.4 × 3.4 米（画布 512×512） |

管理入口：后台 → **广告位**。可以填角标、标题、副标题、底部小字、三种颜色、
排期、权重、上下架，并看到曝光与点击。

几条设计约定：

- **同一位排了多条就轮播**：某个 slot 的条数超过面数时，每 22 秒整体轮换一次。
- **`link` 只有 http/https 会入库**，其它（`javascript:` 之类）在后台保存时就被丢掉。
  填了链接的广告牌可以点，鼠标移上去会变手型；没填的点了没反应。
- **底部小字留空**会自动补「游戏内虚构 · 与现实品牌无关」。这条别删，
  反讽类文案（贷款、婚恋、成功学）不标容易被当成真实广告投诉。
- **前端有内置文案兜底**：后端连不上、后台一条都没配，广场照样有内容。
  但这套内置文案是虚构的，后台一配就被替换，不会混着显示。

## 七、数据概览与访问统计

后台首页现在是**数据概览**，除了原来的玩家与对局指标，还多了一整块访问数据。

### 7.1 数据从哪来

只有一条链路：`js/net/track.js` → `visit.hit` → `visits` 表 → 后台聚合。

- `track.js` 在 `index.html` / `difu.html` / `tiangong.html` 三套场景里都引了，
  每次页面加载在 `load` 之后 800ms 上报一次，**不等它、失败也不提示**。
- 上报内容只有环境信息：访客指纹、场景名、时区、语言、屏幕尺寸、来源域名。
  User-Agent 与 IP 由服务端读请求头，**前端不上报任何游戏内容**。
- 关掉统计：`lib/config.php` 的 `feature.track = false`，接口直接返回 `logged:false`，
  前端不用改一行。

### 7.2 指标口径

| 指标 | 口径 |
|---|---|
| 今日访问 / 累计访问 | 主数字是 **PV**（页面打开次数），小字是 **UV**（按 `vid` 去重） |
| 覆盖地区 | 出现过的地区个数；小字拆成「大陆 N · 其他 M」（其他含港澳台与境外） |
| 七天注册趋势 | 按 `users.created_at` 的日期分组，补零到 7 天，今天那根柱子高亮 |
| 玩家积分排行 | `SUM(lives.score)`，只算 `closed=1` 的已结算对局；同分看单局最高 |
| 玩家资产排行 | `MAX(lives.money)`，即「单局最高资产」，不是当前存档余额 |
| 玩家职业排行 | 按 `lives.job_name` 计数，轴下小字是该职业的平均分 |
| 访问设备 / 浏览器 / 系统 / 入口 | 全量 `visits` 分组计数，百分比以总 PV 为分母（浏览器/系统各取 Top 6，地区 Top 8） |
| 访问地区排行 | 全量 `visits` 按 `area` 分组，百分比以「可识别地区的访问数」为分母（内网、未知不计入） |

> **所有排行面板都是竖向柱状图**，同一套渲染函数 `vchart()`（`admin/index.php` 顶部）：
> 柱高按本组最大值归一，第 1 名高亮，柱顶是数值，轴下第一行是分类名、第二行是小字
> （局数 / 天数 / 平均分 / 占比）。完整精确值在 `title` 悬停提示里，不占版面。
> 数值过万自动缩写（`¥473,300` → `¥47.3万`），否则 8 根柱并排时长数字会互相压字。

### 7.3 访客是怎么认出来的

- `vid`：前端用 `crypto.getRandomValues` 生成 32 位十六进制，存 `localStorage`，
  30 天轮换一次。清浏览器数据就是新访客，所以 UV 是「设备维度」的近似值。
- 没有 `vid`（浏览器禁用存储）时，服务端用 `md5(IP + UA)` 兜底。
- 同一 IP 10 分钟内最多记 90 次（`rate_allow('visit', 90, 600)`），防止刷新刷量。

### 7.4 地区是怎么判的

完全离线，不调用任何第三方接口：

- `lib/geoip_data.php` 是一张 IPv4 区间表（4.1 万段）。**中国段保留原始边界**，
  省级精度实测 99.9%；境外段按 /16 归并，够判断国家。
- 数据来源是 ip2region v1.9.0（Apache-2.0），坐标单位 /24，查询走二分，200 次 0.7ms。
- IPv6、内网、查不到的地址，用前端上报的**时区**兜底（如 `Asia/Tokyo` → 日本），
  再查不到就是「未知」。
- 这张表只在 `visit.hit` 里懒加载，后台页面和其他接口都不会读它。

内网访问（`127.0.0.1`、`10.x`、`192.168.x`）会被标成「内网」，不计入地区排行 ——
本地测试时看到地区排行是空的，属于正常。

### 7.5 保留期与清理

- 写入时有 3‰ 的概率顺手删掉 **365 天前**的日志，避免表无限涨。
- 后台「数据概览 → 访问概览 → 清理旧访问日志」可以手动删 **180 天前**的，分批删，不锁表。
- 访问日志只用来做统计。后台展示的是地区名与聚合数，**不展示单个访客的 IP**。

### 7.6 老库怎么升级

`visits` 是第 25 张表。老库不需要重装：
后台 → 系统设置 → 维护工具 →「检查并修复数据表」，点一下就会补建。
补建之前打开数据概览，访问区会显示一行提示并给一个「去修复数据表」的按钮，不会白屏。

## 八、三界判定（死后去地府还是天庭）

一世走完（撑不住 / 病倒 / 不想动 / 走满一年），前端会判一次归宿：

| 条件 | 去向 |
|---|---|
| 这一世做过恶事（`C.evil >= evil_need`） | `difu.html`（地府） |
| 一件恶事都没做过 | `tiangong.html`（天庭） |

判定成功时，结局卡上会插入一块「三界判定」面板，8 秒倒计时自动跳转，
玩家也可以点「留在这一世」取消。跳转时的地址会带上这一世的履历：

```
difu.html?from=life&e=sick&d=187&j=外卖骑手&g=3&k=2&m=8400&s=34&area=gate
```

两个场景页由 `js/net/realm-gate.js` 负责接住：在页面顶部浮一块「接引牌」，
写明阳寿、身份、善业、恶业、余财、精气，并给一个「回阳世」按钮回 `index.html`。
如果玩家还停在场景的入场页 / 载入页，牌先不弹，只在页底补一行小字，进了场景再浮出来。

### 8.1 后台在哪改

后台 → 系统设置 →「三界判定」，五个字段：

| 字段 | settings key | 默认 | 说明 |
|---|---|---|---|
| 启用三界判定 | `realm_enabled` | `1` | 关掉后结局只停在结局卡，不跳转 |
| 有恶行 → 入地府（%） | `realm_p_hell` | `100` | 判定通过率，不是「恶人里有多少下地狱」 |
| 无恶行 → 上得天庭（%） | `realm_p_heaven` | `100` | 同上 |
| 恶业达到几件算「做过坏事」 | `realm_evil_need` | `1` | 调到 3，就是做满 3 件恶事才判地府 |
| 慈悲线（善业 - 恶业 ≥ N 可改判天庭） | `realm_mercy` | `0` | 0 表示关闭改判 |

改完立即生效，不用重启，也不用清缓存 —— 前端每次进游戏会拉一次。

**概率调低会怎样**：比如地府调到 40，就有 60% 的恶人判完之后卡在结局页，
停留在这一世。适合用来做「不是所有人都会死」的随机感。

**慈悲线怎么用**：设成 5，意味着恶 2 善 8（差值 6）的人可以被改判天庭。
这是给「浪子回头」留的口子，数值调大一点（8～15）就是「大善可抵小恶」。

### 8.2 前端怎么拿到规则

公开接口，不需要登录：

```
GET api/index.php?action=realm.config
→ {"ok":true,"data":{"enabled":true,"p_hell":100,"p_heaven":100,"evil_need":1,"mercy":0}}
```

`js/life/94-online.js` 的 `fetchRealm()` 在启动时拉一次，写进 `window.LIFE_REALM`。
`js/life/90-season-end.js` 的 `realmJudge()` 读这个全局对象。

**接口挂了、数据库没这张表、玩家断网**：一律保持默认值（全 100%），
结局流程照常走，不会白屏 —— `realmJudge()` 只判一次，拿不到就当时机不对。

## 九、事件牌堆与概率

抽事件不是从一个大池子里捞，而是**先抽牌堆、再在牌堆里均匀抽一条**。
这样避免「哪个牌堆条数多，哪个就老出现」。

### 9.1 八个牌堆与权重

权重表在 `js/life/87-turn.js` 顶部的 `YW` 对象里：

| 牌堆 | 数据位置 | 权重 |
|---|---|---|
| `job` 本职业日常 | `ha[jobId]` | 24 |
| `season` 时令 | `ha[seasonId]` | 15 |
| `common` 通用 | `ha.common` | 17 |
| `weather` 天气 | `ha.weather[weatherId]` | 13 |
| `good` 好事 | `ha.fate.good` | 9 |
| `bad` 坏事 | `ha.fate.bad` | 9 |
| `jobGood` 职业好事 | `ha.fate.jobGood[jobId]` | 3 |
| `jobBad` 职业坏事 | `ha.fate.jobBad[jobId]` | 3 |

合计 93。**加权重就是加占比**：想让好事多来点，把 `good` 从 9 调到 14 即可。
调完不需要动别的地方，权重是运行时读的。

抽完之后还要过一道**去重**：最近 26 条出现过的标题（`C.usedEv`）会被跳过并重抽，
最多重抽 26 次，实在抽不到就退回 `common` 第一条。所以同一个梗不会连着两天出现。

### 9.2 事件长什么样

事件库分四个文件，都挂在全局 `ha` 上：

| 文件 | 内容 |
|---|---|
| `js/life/60-data-events.js` | 通用事件 |
| `js/life/61-events-seasons.js` | 时令 / 天气 |
| `js/life/62-events-job.js` | 19 个职业的日常 |
| `js/life/63-events-fate.js` | 好事 27 条、坏事 32 条、链式 21 条 |
| `js/life/64-events-fate-job.js` | 19 个职业各 2 好事 + 2 坏事，共 76 条 |

一条事件：

```js
{ t: "路边躺着一个钱包", d: "……", o: [ { x: "选项文案", ...效果 } ] }
```

选项效果字段：

| 字段 | 含义 |
|---|---|
| `m` | 金额，按职业收入系数缩放；正数吃加成，负数不吃 |
| `amt` | 定额金额，原样进账，不吃任何加成（中奖 1080 万用这个） |
| `pct` | 按积蓄比例扣，实际扣 `(max(0, 钱) + 800) * pct`；+800 是兜底基数，破产时也能扣出钱 |
| `st` / `sp` / `fc` / `rt` | 体力 / 精神 / 体面 / 口碑 |
| `good` / `evil` | 善业 +N / 恶业 +N，三界判定就看这两个累计 |
| `chain` | 排一个后续事件进队列 |

### 9.3 为什么大额损失都写成 `pct`

新增的坏事里，凡是「住院、车祸、诈骗、股票跌」这类动辄上万的损失，
一律写成比例（`pct: -0.3 ~ -0.8`）而不是绝对金额。

原因：这游戏的收入是按职业系数缩放的，前期身家几千、后期几十万。
写死「-45000」，前期一局必死，后期不痛不痒。写成比例，前后期的痛感才一致。

中奖反过来，用 `amt` 写死 1080 万 —— 这种一夜暴富就该是绝对数，不然穷人中了没感觉。

### 9.4 链式事件

有些事不是当场结束的：买了彩票要等开奖，牙疼要等复发，股票跌了要等第二天继续跌。

```js
chain: { after: 2, roll: [["lot_big", 0.008], ["lot_mid", 0.06], ["lot_small", 0.22], ["lot_none", 0.712]] }
```

- `after`：隔几次踩事件格之后唤出（2 就是再踩两次事件格）
- `id`：直接指定后续事件
- `roll`：按概率摇一个后续事件，权重总和应为 1

队列存在 `C.chain` 里，最多 4 条，先进先出；每次踩事件格先 `--after`，归零就唤出，
唤出的事件优先于当次抽签。链式事件本身也可以再带 `chain`，目前只用了两层。

### 9.5 加新事件要注意什么

1. **标题不能重复**。去重是按标题做的，重名会导致其中一条永远抽不到。
2. **金额量级要跟现有库对齐**。拿不准就用 `pct`。
3. **职业事件必须挂在对应职业的 key 下**，否则所有职业都能抽到，出戏。
4. **善业恶业要成对出现**。只加恶不加善，全服都会下地狱。

## 十、命运扩展（改命 · 卜卦 · 图鉴 · 命运卡组 · 审判）

这一层全在 `js/life/95-fate-extra.js` 和 `96-run-mod.js` 里，加上地府天庭页的
`js/net/realm-trial.js`。**没有改动任何原模块的源码**，全部用运行时包装接在原函数前面，
所以老库升级只要把新文件拷进去就行。

### 10.1 改命：拿恶业换一次重掷

棋盘右下角的「问卦」按钮（`#fgBtn`）→ 改命页 → 掐指改道。消耗 1 点恶业，
系统掷两次骰子，玩家挑一个走。

这不是便利功能，是把恶业从"死亡判定的计数器"变成"可花掉的资源"。同时配了反向刹车：

- 每 1 点恶业，`YW.good` 权重 −1（最低留 2），做好事的机会变少
- 恶业 ≥ 3 时开「报应」牌堆，权重 `min(14, 2 + (恶业−3)×2)`

结果就是：作恶能买到眼前的运气，赔掉的是往后的运气。要不要换，玩家自己算。

### 10.2 善业挡灾 / 替身

体力或精神归零时，如果账户上压着 10 点善业，自动触发一次「有人替你扶了一把」：
消耗 10 善业，回 30 点。一次性。

命运卡「替身」优先于善业，不扣善业，回 45 点。

两个都在 `ds()` 的包装里拦，`ds()` 是全局唯一的死亡判定入口（`r_`、`qx`、`Eu` 都走它），
所以没有漏网的路径。

### 10.3 卜卦：看接下来的牌面

500 块，把当前牌堆权重跑 600 次抽样，给出「职业日常 25.8% / 杂事 18.3% / 好事 9.7%…」
和一句判词。**不消耗真实牌堆**，不会打乱顺序，纯粹是情报。

恶业越高，卦面越阴沉——因为 `good` 权重真的被压下去了。

### 10.4 图鉴

`js/life/95-fate-extra.js` 把 `ha` 里所有事件摊平（332 条），遇到一条点亮一条，
本地存 `life_codex_v1`，登录后同步到 `life_codex` 表。

分类统计：好事 / 坏事 / 报应 / 职业好 / 职业坏 / 杂事 / 季节 / 职业日常 / 天气 / 后续。

### 10.5 命运卡组

开局点「就这样走」之后先弹 12 张卡，挑 3 张。吉与险混着来：

| 吉 | 险 | 中 |
|---|---|---|
| 横财 +¥8,000 | 煞星 +¥15,000，前 3 次事件必坏 | 命数：改命白送 3 次 |
| 铁打：体力上限 +25 | 孽债 +¥20,000，恶业 +4 | 替身：一次免死 |
| 钝感：精神上限 +25 | 搏命 +¥12,000，体力上限 −20 | 抠门：开销减半，体面 −8 |
| 贵人：前 3 次事件必好 | | 前世记忆：继承上局 25% 存款，恶业 +1 |
| 人脉：每天多进 ¥40 | | |

贵人和煞星同时带会互相抵消（`forceLeft` 归零），不叠加。

实现靠包 `Dc()`：第一次调用只弹面板，选完再真正开局，然后 `applyDeck()`。
注意顺序——属性必须在原始 `Dc()` 铺完之后加，否则会被初始化覆盖。

### 10.6 每日一命

`index.html?daily=1` 进入。种子 = 当天日期（如 `20261028`），用 mulberry32 替换
`Gx()` / `Yx()` / `Lc()` 三个函数里的 `Math.random`。

牌序固定，抽到第几张取决于你走了多少步——这是 Roguelike 日赛的标准做法。
问卦面板的「今日」页里有入口，同一天只能开一次（`life_daily_<种子>`）。

验证过：同一天重开两次，前三次 `Gx()` 完全一致（5/3/1）。

### 10.7 全服善恶天平

`action=world.balance`（公开接口，不需要登录）按最近 7 天聚合 `life_karma_log`：

- 恶 > 善 × 1.35 → `state=yin`，好事权重 ×0.78、坏事权重 ×1.22
- 善 > 恶 × 1.35 → `state=yang`，反过来
- 样本 < 30 不下判断（否则头三个人就能把天道带偏）

HUD 顶部会多一个「天道 · 阴盛 / 阳盛 / 中平」的小字徽标，鼠标悬停看具体数字。

权重是临时叠的：`Yx()` 包装里改 `YW.good` / `YW.bad`，`finally` 里还原，
不污染全局牌堆。

### 10.8 因果债（玩家之间）

A 做了一次恶事 → `debt.owe` 从 `life_lives` 里随机挑一个真实玩家当债主，
写进 `life_debts`。债主下次开局时 `debt.pull` 取一条未取走的，塞进 `C.chain`
（`after: 2`），第 2 个事件格撞见「欠你的那个人出现了」。

这条事件有三个走向：算清楚（拿钱）/ 算了（善业 +1）/ 反过来敲一笔（恶业 +1）。

### 10.9 三界审判

地府和天庭不再是"打个卡就走"。接引牌下面多一个按钮：

**地府 · 孽镜台 → 孟婆桥 → 六道轮回**

- 孽镜台把这一世做过的恶事一件件照出来，可以「认」，也可以「辩」（消耗 1 点善业抵消 1 件）
- 辩光了，镜面全白，判官合上簿子什么也不写
- 孟婆汤三档：全喝（清零）/ 喝七成（继承 30%）/ 一口不喝（全继承，但带恶名）
- 六道：人道（+¥3,000）/ 畜生道（体力上限 +30，钱 −¥3,000）/ 饿鬼道（+¥15,000，精神上限 −30）/ 修罗道（+¥8,000）

**天庭 · 受封**

没恶事可审，直接挑一个仙职：掌福（下一世 +¥10,000）/ 掌寿（体力上限 +20）/ 掌明（精神上限 +20）。
天庭不喝汤，善业全数带走。

结果写 `localStorage.life_next_v1`，`index.html` 开局时读一次、用完即删（超过 24 小时作废）。

### 10.10 新增的三张表

```
life_karma_log   善恶流水（world.balance 的原料）
life_debts       玩家之间的因果债
life_codex       事件图鉴收集
```

都在 `sql/schema.sql` 里，`lib/schema.php` 的必存在表清单也加了。
老库升级：后台 → 系统设置 → 「修复数据表」跑一遍即可（`CREATE TABLE IF NOT EXISTS` 不会动老数据）。

**为什么不用给 `lives` 加 `evil_cnt` 字段**：一键安装要求 `CREATE TABLE IF NOT EXISTS` 就能搞定，
加列得写 ALTER，还得考虑列已存在的情况。多一张流水表省掉一堆判断，而且善恶本来就是过程数据。

## 十一、关于 UGC

本项目**不接收任何玩家自由文本**：

- 漂流瓶、隔世信、望乡台回应、判官辩护词，全部从 `lib/presets.php` 的预置文案里「选一条」，服务端只存 `key`。
- 业力遗产的文案由系统按 `kind` 模板 + 职业名自动拼装。
- 因此没有投稿、没有审核队列、没有内容风险。

## 十二、常见问题

**装完打开是 503 `not_installed`**
`lib/config.php` 没生成成功，检查 `lib/` 目录权限。

**接口一直 401**
令牌存在 `localStorage` 的 `life_token`，换域名或清了缓存就会掉，重新登录即可。

**排行榜一直是空的**
`rank.list?type=score` 只统计 `closed=1` 的对局，也就是真正走完一世并结算过的。

**想让全服天气立刻变**
后台 → 世界状态 → 手动干预，改完立刻广播，所有在线玩家下次请求即生效。

**想关掉某个玩法**
改 `lib/config.php` 里 `feature` 段的开关，保存即生效（`lifeloan` 借寿默认关闭，因为平衡风险高）。

**安装时提示 `Table 'xxx.life_users' doesn't exist`**
这是 v1 安装器的分句缺陷：它按「分号+换行」切 SQL，又把以 `--` 开头的整段当注释丢掉，
结果每张表前面的注释横幅把 `CREATE TABLE` 一起带走了 —— 表只建出 2 张，随后创建管理员就报 1146。

v2 已改为按字符扫描的分句器（识别引号、反引号、行注释、块注释，只在引号外断句），
并在建表后强制校验 25 张表是否齐全，缺表会直接告诉你缺哪几张、失败原因是什么。

修复步骤：
1. 用新的 `install.php` 覆盖服务器上的旧文件（其他文件不用动）
2. 重新提交安装表单即可。已存在的表会被 `IF NOT EXISTS` 跳过，**不需要删库**
3. 如果仍然失败，把 `schema.sql` 里的 `{{P}}` 全部替换成你的前缀（默认 `life_`），
   用 phpMyAdmin 或 `mysql -u root -p 库名 < schema.sql` 手动导入，再回安装页重试

**已经装过了，新版本的广告位表怎么补**
后台 → 系统设置 → 维护工具 →「检查并修复数据表」。它会把 `sql/schema.sql` 补跑一遍
（全部是 `CREATE TABLE IF NOT EXISTS`，已有数据不受影响），建完表顺手写 12 条默认广告。
不用重装，也不用进数据库。

**广告位改了但前台没变**
前台每次进游戏时拉一次 `ads.list`，刷新页面即可。若还是旧的，检查这条广告的
`status`（要上架）和排期（`start_at` / `end_at` 是否把今天排除在外了）。

**权限不足导致建表失败**
报 `CREATE command denied` 就是数据库账号没有建表权限。到主机面板给该账号授
`SELECT,INSERT,UPDATE,DELETE,CREATE,ALTER,INDEX,DROP`，或直接用 root 安装。

**死了却不跳地府 / 天庭**
按顺序查三处：① 后台「三界判定」里的「启用」还勾着吗；② 两个概率是不是被调成 0 了；
③ 这一世到底有没有做恶事（恶业 0 就是上天的路线，`evil_need` 调高会让人「不够格下地狱」）。
三条都正常还是不动，打开控制台看 `location.href` —— 判定成功时地址栏会先出现 `difu.html?from=life&...`。

**想调「好事 / 坏事」出现的频率**
改 `js/life/87-turn.js` 顶部的 `YW`，里面八个数字就是八个牌堆的权重。
把 `good` / `bad` 调大，命运牌堆占比就上去；调成 0，就退回纯日常事件。
改完刷新页面即可，不需要重新构建。

**想加自己的事件**
好事坏事加在 `js/life/63-events-fate.js`，职业专属加在 `64-events-fate-job.js`。
字段说明见上一章第 9.2 节。**注意标题不能和现有事件重名**，重名的那条会永远抽不到。
